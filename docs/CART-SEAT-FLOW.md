# جریان سبد خرید صندلی‌دار — 1.0.0

## محدوده و معماری

- منبع حقیقت موجودی: `session_seats` + `holds` در InnoDB. Woo Cart تنها پیش‌نمایش سبد و قیمت غیرقطعی است؛ Woo order تنها از `CheckoutService` ساخته می‌شود.
- `GET /sessions/{id}/layout` و `/availability` نقشه و وضعیت عمومی را می‌دهند؛ `GET /cart/preview` فقط موجودی متعلق به Hold داخل Woo session را می‌دهد. توکن Hold در سرور باقی می‌ماند.
- نگهداری موقت حداکثر ۱۰ دقیقه و با امکان تمدید محدود از مسیر قبلی است. تغییر جایگاه TTL را افزایش نمی‌دهد.

## جریان عملیاتی (staging)

1. کاربر مهمان در `[pesm_seat_map]` صندلی انتخاب کرده و Hold واقعی می‌سازد.
2. با «انتقال رزرو به سبد خرید»، REST با bearer Hold و اطلاعات شرکت‌کنندگان (اختیاری) درخواست attach می‌کند. Woo session یک Cart item با شناسه Hold و توکن خصوصی ذخیره می‌کند؛ محصول مخفی از فروش مستقیم محافظت می‌شود.
3. در Cart کلاسیک پنل نقشه با هوک `woocommerce_after_cart_table` و در صفحات سفارشی با `[pesm_cart_seats]` نمایش داده می‌شود. برای Cart Blocks، افزودن دستی Shortcode لازم است؛ این مسیر یک block extension رسمی نیست.
4. هنگام جایگزینی، سرویس ابتدا Hold و مالکیت را دوباره می‌خواند، سپس `HoldService::modify()` تراکنشی را فراخوانی می‌کند. تنها پس از commit SQL، `pesm_cart_seat_ids` و quantity مربوط به همان آیتم در Woo session اصلاح و cart totals تازه می‌شوند.
5. «ثبت سفارش آزمایشی از سبد» همان `CheckoutService::prepare` را فراخوانی می‌کند؛ در موفقیت، آیتم از Cart حذف و اطلاعات دسترسی مهمان/لینک پرداخت نمایش داده می‌شود. درخواست پرداخت تکراری باید به همان سفارش قبلی هدایت شود.

## کنترل امنیت و شکست

- `X-PESM-Hold-Token`: شناسه bearer برای attach، فقط در هدر HTTPS؛ همیشه به hash در جدول نگهداری‌ها تطبیق داده می‌شود.
- `X-PESM-Cart-Nonce`: توکن تصادفی ۲۵۶ بیتی اختصاصی **نشست Woo** برای preview/replace/complete؛ همراه با کوکی session، کنترل Origin و Rate Limit. HTML فقط nonce نشست و شناسه Cart را دارد، نه توکن رزرو.
- درخواست‌های هم‌زمان ممکن است پس از commit Hold و پیش از ذخیره Cart خطا دهند؛ Cart تا همگام‌سازی مجدد معتبر نیست و نباید از آن مستقیماً به درگاه رفت.
- صندلی‌های یک Hold متعلق به هیچ Cart دیگری تلقی نمی‌شوند مگر با possession توکن. یک نشست با کلید guessed نمی‌تواند رزرو دیگری را تغییر دهد.
- حذف line از Cart آزادسازی Hold را **تلاش** می‌کند، ولی Hold تبدیل‌شده به `payment_pending`/`sold` هرگز از این طریق آزاد نمی‌شود.
- تغییر quantity پیش‌فرض Woo رد می‌شود. خطای Stores API Cart قبل از ساخت Checkout order از `woocommerce_store_api_cart_errors` برگردانده می‌شود؛ `woocommerce_store_api_checkout_update_order_from_request` دفاع ثانویه است. این قفل‌ها باید روی نسخه Woo واقعی با روش‌های Checkout کلاسیک و Blocks آزمایش شوند.
- نام شرکت‌کننده برای صندلی تغییرنکرده در WC session حفظ می‌شود؛ برای صندلی جدید در صدور سفارش، نام خریدار پیش‌فرض است. هنوز UI اختصاصی ویرایش شرکت‌کننده در Cart وجود ندارد.

## محدودیت‌های شناخته‌شده

- **Woo Blocks native checkout، HPOS، Store API payment flow و test gateway روی وردپرس واقعی تأیید نشده‌اند.** پنل فقط از Cart به سفارش مستقیم قبلی هدایت می‌کند.
- چند جلسه در سبد می‌توانند آیتم‌های مستقل داشته باشند، اما هر دکمه فقط یک سفارش Woo ایجاد می‌کند؛ یک سفارش ترکیبی واحد وجود ندارد. Cart سایر کالاهای فروشگاه دست‌نخورده می‌ماند.
- مالیات/کد تخفیف/گزارش پولی کامل، تغییر جایگاه پس از صدور بلیت، refund reconciliation و PDF شامل این تغییر نیستند.
- سناریوی ۲۰ PHP Worker و ۱۰۰ بازدیدکننده واقعی اجرا نشده است؛ کارکرد روی WooCommerce Cart کلاسیک و Blocks بدون E2E هنوز قابل تضمین نیست.

## آزمون‌های این مرحله

- `php tests/cart-seat-bridge-fake-wc.php`: شبیه‌ساز WC Cart/Session/DB برای attach و پیش‌نمایش با nonce، منع direct add/checkout و محافظت از اطلاعات شرکت‌کنندگان؛ جایگزین InnoDB/Woo واقعی نیست.
- اجرای همه تست‌های مستقل قبلی، php -l و node --check.

## معیار پذیرش باقی‌مانده

- در staging با WordPress/WooCommerce واقعی: افزودن/تغییر/حذف آیتم‌های مختلف، Cart Classic و Blocks، احیای نشست، ارسال سفارش رایگان/پولی، اختلاف قیمت و انقضا، خروج کاربر و کوکی‌های چند مرورگر، هم‌زمانی ۲۰ کاربر برای یک صندلی، عدم افشای توکن یا تغییر مالکیت؛ سپس حداقل ۱۰۰ کاربر هم‌زمان و تست امنیت.
